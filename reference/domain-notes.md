# Domain notes carried forward from the old model

Extracted from code comments in the pre-rewrite `hemonc_alchemy/model/hemonc_model.py` before that file was deleted (per [hemonc-alchemy-spec.md](../_design/hemonc-alchemy-spec.md) US-29 — hard-won domain knowledge is worth keeping even when the code it lived in isn't). None of this is wired into anything; it's context for whoever ports the equivalent logic into `model/` or `compiler/`.

- **Regimen parts are reused across containing regimens.** e.g. `AC` (doxorubicin+cyclophosphamide) is defined once as a regimen part and then reused inside `AC-TH`, `AC-THL`, etc. The n-m mapping table between regimen parts and their containing regimens exists specifically to support this reuse — don't model regimen parts as owned 1:1 by a single regimen.
- **A regimen always has at least one regimen part, even a single-part regimen.** The old model's comment: "If a regimen contains only one regimen part, the regimen part covering the whole regimen is still defined." Don't special-case single-part regimens as partless — this was a deliberate normalisation decision, not an oversight.
- **`was studied in` is a first-class relationship**, backed by an explicit n-m mapping table between regimen (variant) and studies — this is the same variant↔study linkage that `hemonc_import`'s `relationships.py`/`toolbox/linking.py` resolves today via fuzzy token matching rather than a clean join table. Worth considering whether a maintained mapping table (rather than resolve-on-read token matching) is the more correct long-term shape, if HemOnc's own dictionary ever exposes this as a real key relationship instead of pipe-delimited free text.
- **Component role ambiguity**: a "role" in a regimen context can be filled by either a component (drug) or a component *class* — the old model notes this forced a synthetic ID specific to that mapping table rather than a nullable FK to either side, "because a role can have either component or component class as the included member."
- **Open design question the old model never resolved**: "do biomarker and condition belong directly in the context, or is it a multi-way n-m relationship?" — flagged as an open question in the old code, never actually settled. Worth a deliberate decision this time rather than leaving it ambiguous.
- **Cycle/timing modeling was flagged as unfinished** even in the old model: a `TODO: consider re-working a 1:n map with timing for cycles / weeks etc?` sat next to a commented-out `timing` relationship that was never activated. This maps onto the same territory `schedule_handling.py`/`schedule_properties.py` cover in `hemonc_import` today (and onto the confirmed "indefinite dosing schedules silently dropped" bug from the audit) — this has apparently been a soft spot across two generations of this model, worth extra scrutiny rather than assuming the current schedule-handling code has it fully solved.
